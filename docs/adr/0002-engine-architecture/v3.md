# 2. Engine architecture: backend layers and what each one owns

- **Version:** 3 (2026-10-12). [v2](v2.md) is the 2026-10-07 version; [v1](v1.md)
  is the 2026-09-17 design, written before any of it was built.
- **What changed from v2:** a second model and controller landed, an embedding
  model (`embed_model.py`, `embed_controller.py`, spec 0007). §3 says a
  controller feeds its model texts as well as prompts, and that checks and a
  parser come only with a prompt; §5 adds `Embedding`; §8 adds the embedding
  model's slots; "Structure today" lists the new files. No rule changed.
- **Status:** Accepted
- **Scope:** all of `engine/`. Existing code that breaks these rules is
  migrated to its layer or deleted; it is not grandfathered.
- **Repositories layout:** [ADR 0003](../0003-repositories-one-folder-per-data-source/)

## Context

The first extraction pipeline (ADR 0001 v1) put every responsibility in
`engine/pipeline/`: a 594-line `run.py` held the worker pool, resume, poison
guard, manifest, progress and the per-record loop, while `models/` and
`controllers/` sat empty. Inputs and outputs were dict-shaped convention, and
progress was `print` inside the loop. That code is deleted.

The layer names below are **definitions set by the project owner** and differ
from common MVC convention deliberately. They are not re-derivable from the
names alone.

## Decision

### 1. `engine/` is the backend; frontends live outside it

`engine/` is a library. Notebooks are its frontend today; a CLI would sit
beside `engine/`, not inside it, as a peer of the notebooks.

A frontend owns argument parsing, output formatting, exit codes and display. It
owns **no workflow logic**: if a frontend has to decide something about
purpose/risk extraction, that decision is in the wrong layer.

The test: *could a notebook do everything the CLI does, importing `engine`
alone?* If not, something the CLI needs is trapped inside it.

### 2. A workflow is a packaged series of services — convenience, not a wall

`engine/pipeline/` is where entry points go (`start`, `resume`, `smoke`,
`retry`) once a workflow needs one. None exists yet: notebooks call services
directly, which is allowed. Nothing below `pipeline/` is private by
convention.

### 3. The layers, and what each owns

| Layer | Owns | Does not own |
|---|---|---|
| `repositories/` | the entry to get or save data | where the data physically lives — that is behind it |
| `models/` | an actual model (LLM, embedding, NLP): its own lifecycle **and** its hosting strategy | any knowledge of the workflow using it |
| `controllers/` | driving one model: creating and readying it, feeding it prompts or texts, running checks and parser, retries, progress | any data of its own |
| `services/` | the workflow's own logic — everything touching no model | how a model is hosted or executed |
| `pipeline/` | entry points that package services into a workflow | logic that belongs in a service |

**`repositories/` is the entry to get or save data.** `loader.py` is the only
way to read a data source, `store.py` the only way to write it. Where the data
lives is behind them (ADR 0003).

**`models/` means actual models, not data shapes.** The model loads itself,
checks its own memory, enforces one instance, closes itself. **It also owns its
hosting strategy** — `qwen_model.py` runs `llama-server`, and nothing above it
knows a server exists.

**`controllers/` are per model, not per workflow.** The controller creates its
model; a service never builds one. It runs the checks and the parser that come
with the prompt (`repositories/prompts/<id>/`), retries failures within a
budget, and relays progress. An embedding has no text to validate, so
`embed_controller.py` has no checks and no parser: it batches texts, retries
failed requests and relays progress. **There is no workflow-level controller.**

**Dependency direction.** A module imports only its own layer or a layer below
it:

```
pipeline → services → controllers → models
                                  ↘ repositories
```

`repositories/` may import `models/` for the types a prompt is checked against
(`Check`, `Generation`, `Prompt`); `models/` imports neither. `engine/config.py`
and `engine/notify.py` are shared by every layer and import no layer.
`tests/test_layers.py` enforces this.

### 4. Everything a layer takes and returns is explicit

- **Services declare input and output as types**, not dict-shaped convention.
- **Models report usage per generation** (tokens, latency).
- **Controllers turn that into progress** (done of total, throughput, ETA over
  the wall clock) and hand it to an `on_progress` callback. A frontend that
  wants to display it subscribes; one that does not gets a quiet library.

### 5. Schema travels with its producer

No global `schemas/` directory. `Label` lives in `repositories/dsld/labels/`
with the loader that produces it; `Generation`, `Prompt` and `Embedding` in
`models/base_model.py`; `CleanedLabel` with the cleaning service.

### 6. Services return values; frontends render

A service hands back data. Composing text for a person — a diff, a table, a
progress bar — is rendering, and belongs to the frontend.

### 7. No folder named for a sequence position

`preprocessing/`, `processing/`, `postprocessing/` are rejected. They say
*when*, not *what*, and stop being true the moment a workflow reorders or adds
a stage. `tests/test_layers.py` enforces this.

### 8. Concurrency is the model's decision

The controller hands the model prompts and keeps a fixed number in flight; it
never learns a slot count. How many run at once is the model's business:
`qwen_model.py` runs `n_parallel` slots, set in `configs/qwen.toml`, and says
per prompt whether it fits a slot; `embed_model.py` does the same for texts,
set in `configs/embed.toml`. The embedding controller sends texts in batches,
so what it keeps in flight is requests of `batch` texts.

## Structure today

```
engine/
├── config.py, notify.py          shared by every layer
├── repositories/                 ADR 0003
│   ├── dsld/{raw,labels,runs}/
│   └── prompts/                  loader.py, schema.py, purpose_risk/, label_clustering/
├── models/                       base_model.py, qwen_model.py, embed_model.py
├── controllers/                  qwen_controller.py, embed_controller.py
└── services/
    ├── dsld_cleaning/
    ├── purpose_risk/
    ├── extraction/               pre-ADR: to migrate or delete
    └── sources/                  pre-ADR: DSLD and PubMed fetching is repository work
```

## Consequences

- A model can be swapped or rehosted without touching a service.
- More files and more indirection between a notebook call and the model call.
- `services/extraction/` and `services/sources/` predate this ADR and still
  have callers (notebooks, two tests, `benchmarks/parallel_slots.py`); moving them is open work under the
  scope line above.

## Open question
